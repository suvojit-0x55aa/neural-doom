# Replaceable Doom core

The native shell owns the window, event collection, monotonic scheduling, local file access, audio-device I/O, Metal submission, and presentation. Those are host responsibilities. Logical sound/music event selection remains circuit-owned; the host only delivers those events to the device. The destination is a **composable network of exact frozen circuit modules** over bounded state arrays, scheduled explicitly, until no DoomGeneric gameplay or renderer code executes. The current baseline is an executable specification and parity oracle.

## Current boundary

`Sources/DoomCore/g_game.c` is the sole patched gameplay adapter. Before mouse consumption it captures a 24-cell `HMMovementInput` and the 51 pre-command cells of a 55-cell `HMTicRemainderInput`. The original `G_BuildTiccmd` computes the same-tic C reference. `HM_EvaluateMovement` commits the circuit's `forwardmove`, `sidemove`, raw `angleturn`, and carried `turnheld`; those four committed values complete the remainder input. After the remaining original C rules run as oracle, `HM_EvaluateRemainder` commits a 21-cell result: final angle and every other command field, double-click state, low-resolution turn carry, mouse state, and edge-trigger flags. Thus both command modules own the supported tic before the game ticker. Either module explicitly commits C on domain rejection, Metal failure or its 2 ms deadline, or parity mismatch. Eight preallocated input/output slot pairs per module isolate late Metal commands. `Sources/Bridge/MovementABI.h` and `TicRemainderABI.h` are stable version 1 C-facing contracts; Swift and UI code do not read DoomGeneric gameplay globals. [locomotion-graph.json](locomotion-graph.json) and [tic-remainder-graph.json](tic-remainder-graph.json) are the generated graph records; tests check both manifests byte-for-byte.

The engine queue is the single owner of reference C state. `singletics` makes each `HM_EngineFrame` execute one command and one simulation tic; `TicScheduler` may issue several such calls between two MTKView presentations. Each oracle/circuit pair receives the same captured input, and C consumes mouse state once. Each module has a dedicated Metal-attempt queue and a 2 ms engine-side deadline. A late worker result is discarded and its preallocated slot stays isolated until completion. The engine spin-polls short completion waits because timed semaphore wakeups caused severe overshoot in WAD traces; this spends some CPU during the wait. An OS scheduling pause can still overshoot a wall-clock deadline, so pacing is measured in real play traces. The inspector's pause stops calls at tic boundaries, step issues one call, and resume resets the scheduler wall-clock baseline. The panel reads sampled live results from both circuits. Off mode writes no operation-value trace; on mode samples locomotion once per four tics and remainder once per eight tics into separate 128-entry drop-oldest rings. Attempt latency includes worker dispatch and Metal submit/wait; layer values are CPU replay data, **not** per-layer GPU time.

The locomotion exact domain is binary buttons, joystick axes -1/0/1, mouse X -256…256, mouse Y -8192…8192, `ticdup` 1…4, and incoming `turnheld` 0…16,777,212. The remainder ABI additionally validates all 55 snapshot cells, including weapon enums/ownership, double-click counters, low-resolution carry, chat byte, and consistency value, against the bounds in `HM_RemainderInputInDomain`. The circuits use FP32 exact integers under these bounds with ordered affine, ReGLU, and index-read instructions; Metal compiles with safe math. Domain validation runs before GPU dispatch. Out-of-domain values never index circuit tables. The locomotion input ABI's reserved cell is ignored in this version.

## CircuitModuleV1 destination ABI

`Sources/Bridge/CircuitModuleABI.h` and [the frozen contract](contracts/CircuitModuleV1.md) encode the version 1 envelope. Each future module receives immutable input, state, table, and prior-event spans with both counts and caller-owned capacities, plus ABI/program/encoding versions, module/tic IDs, and source hash. The caller also supplies the required output count and bounded output, state-delta, and event capacities. Results echo the invocation identity and retain the same caller-owned pointers/capacities. Deltas use stable `(array ID, element index, cell ID)` coordinates; events are strictly ordered by `(phase, emitter slot, local sequence)`. Any invalid identity/version/hash, count, pointer pairing, table bound, ordering, integer operation, or partial result produces a non-exact status with all three result counts reset to zero. A sampled trace token is scheduler metadata rather than a gameplay output. Module output is staged, validated, then committed by `CircuitScheduler`; a failed module cannot partly mutate the world.

`CircuitModuleV1` does not impose one global content limit: every span declares its count and allocated capacity, table views declare length/capacity, and each later manifest freezes module-specific maxima. `HMWorldSnapshotV1`, `HMModuleEventV1`, and `HMDrawPrimitiveV1` are canonical pointer-free records; runtime pointers exist only in bounded C views. Numeric IDs are explicit in `CircuitIDs.h`, `WorldStateABI.h`, and [registry-v1.json](contracts/registry-v1.json), with reserved T05-T13 ranges. Registration/discovery order cannot change an ID.

The merged locomotion and tic-remainder graphs retain their existing FP32 ABI, operation IDs, manifests, and accepted domains byte-for-byte. Their documented bounds are the range proof for encoding `fp32-exact-v1`. Future modules use the separate `exact-i32-u32-v1` program ABI: raw 32-bit registers, checked signed add/subtract and 16.16 fixed multiply/divide, wrapping unsigned angle addition, comparisons/gates, and bounds-checked indexed reads. CPU and MSL evaluators never convert those registers through `Float`. Canonical serialization is field-wise little-endian with no pointer or padding bytes, and FNV-1a-64 hashes the serialized bytes. A semantic change requires a new ABI/schema/encoding version; an accepted-domain, capacity, graph, root, or operation change requires a new manifest/program version and source hash. Existing IDs and meanings are never reused.

During migration, each module ledger entry is one of `reference-C`, `dual-run`, or `circuit-owned`. `reference-C` owns state; `dual-run` commits C and compares a circuit candidate; `circuit-owned` commits exact circuit output while C remains an optional oracle/fallback. Both tic-command entries are circuit-owned; reference C remains the explicit safety path. Ownership is per module and per state cell, so no app feature may depend on an unversioned DoomGeneric global. `Docs/circuit-coverage.json` is the authoritative machine-readable module list, ownership ledger, and coverage count; the count describes enumerated core modules, **not** instruction coverage.

## WAD-to-circuit memory and capacity policy

The host parses an IWAD/PWAD directory and decodes map lumps into versioned bounded tables: vertices, linedefs, sidedefs, sectors, nodes, subsectors, segs, things, blockmap, textures, flats, and sprite metadata. Table handles and per-map lengths are inputs to circuit modules; the application does not bake one level into weights or shader code. A loader checks lump bounds and map-derived capacities before a level commits. Maps fitting a module's declared limits use exact circuit memory/index reads. While the reference exists, overflow or unsupported features select reference C for the affected module/tic and increment visible counters. After reference removal, unsupported content yields a clear load error; it never truncates arrays or silently approximates behavior. Capacity limits and maximum observed occupancy are manifest fields and become acceptance tests for each migrated module.

The scheduler order is input normalization → tic commands → player movement and collision → interactions/combat → thinker/AI transitions → world commit → HUD/automap → BSP traversal → tiled rasterization → host presentation. Modules exchange bounded state and event arrays, including explicit sound, spawn, pickup, and sector-change events. Deterministic RNG state is a circuit cell. The host submits circuit kernels and presents pixels, but it does not reimplement rules. Migration gates require generated C-vs-circuit snapshots, WAD-backed traces, exact outputs and state deltas, capacity tests, and measured latency/frame pacing. Once all ledger entries are circuit-owned, remove `Sources/DoomCore` from the application target and confirm a reference-free build and play trace.
